# 性能测试与优化（2026-11-27历史记录）

记录日期：2026-11-27。正式运行入口为 `game/` 的 Godot 4.7.2 工程，H5 与 Dora 共用内容包。

## 改动

- 骨骼求解缓存关节索引、静态骨长和静止姿势；同一模拟时刻不重复计算。运动、转身、工种、加工阶段、负重、攻击和运输状态变化会使缓存失效。父节点变换也参与判断。
- 两段肢体直接计算父子相对旋转，减少每写入一个关节就重新查询整条骨架的次数。
- 静止单位不重复写入位置、朝向和可见状态，避免向场景树传播无变化的变换。
- 单位避让使用一格宽的空间桶，只检查相邻九格。推开顺序、半径、地形阻挡和位移公式保持原规则；单位跨桶后更新查询。
- 部队、建筑使用 ID 索引；搜索敌人只遍历敌方列表，保留原有距离算法、优先级和同距选择顺序。

模型、阴影、抗锯齿、分辨率、单位数量、战斗规则和动画质量参数未降低。

## 测量方法

硬件为 i5-12400F（6核12线程）、RTX 4060 Ti 8GB，Windows，NVIDIA 581.80；H5 使用 Edge 158 硬件 WebGL 2。项目 `msaa_3d=2` 是 Godot 的 **4× MSAA 枚举**。

原生对照使用1280×800窗口、关闭垂直同步和帧率上限。固定1/60秒引擎时间步，每场预热480帧、采样600帧，以 A/B/A/B 交替执行。固定时间步用于保持两版模拟过程相同，采集的墙钟耗时不表示60FPS显示输出。比较器核对开头/结尾玩法摘要快照及绘制数量。六场景包括村落、九设施生产、77单位驻军、125单位交战、驻军全景和暂停；除村落外是明确注入资源/军队的压力夹具，交战提高生命值以持续测量，不能视为正常经济游玩。

基线和优化版使用同一套计时探针。计时位于游戏 `_process` 内，分为模拟、镜头、画面同步和HUD，逐帧采样 `RenderingServer.frame_post_draw`。这是引擎渲染回调，并非GPU计时或物理屏幕呈现时间；未以浏览器RAF回调数冒充游戏帧率。已用人为8毫秒延迟检查分段归因及渲染帧编号递增。计时期间不截屏、不读回图像，也不并行构建或运行其他验收。

当前电脑有其他程序共享CPU/GPU。每秒记录整机CPU、游戏进程CPU/RSS及竞争进程，帧尾数据仅描述此环境；优化结论以匹配内容的脚本开销为主，不承诺普通笔记本、真实手机或所有Dora宿主稳定60FPS。

H5测量通过真实鼠标键盘操作，覆盖村落、建设、募兵、全景和暂停。逻辑画布1600×1000、DPR1、4× MSAA；无头硬件浏览器结果不能替代真实显示器/手机帧率。记录引擎静态内存、JS堆及浏览器/渲染器/GPU等进程RSS总和；RSS含共享页重复计数，不能直接当作独占物理内存。

## 复现

```powershell
python scripts/check-performance.py
python scripts/benchmark-performance.py --output .build/performance/native --duration 10 --deterministic
python scripts/serve.py --port 8767
python scripts/benchmark-web-performance.py --output .build/performance/web --seconds 10 --restart-cycles 5
```

`--deterministic` 仅用于性能夹具的固定时间步，不改变正式游戏启动方式。H5 的 `?profile` 和原生的 `--profile` 只启用有界的只读观察；默认关闭。基线在 `.build/performance/baseline/`，对照原始帧、负载、统计和验证收据在 `.build/performance/`；不随运行包分发。

## 原生对照结果

每场两轮各600帧，以下按同场景合并统计。单位为毫秒/帧。脚本包含模拟、镜头、画面同步与HUD；整帧是渲染回调间隔。

| 场景 | 脚本平均：基线 → 优化 | 减少 | 整帧P95：基线 → 优化 | 整帧P99：基线 → 优化 |
| --- | --- | --- | --- | --- |
| 村落 | 3.25 → 0.99 | 69.5% | 10.10 → 14.11 | 14.23 → 20.24 |
| 九设施生产 | 3.91 → 1.98 | 49.3% | 9.35 → 13.45 | 10.89 → 18.06 |
| 77单位驻军 | 13.87 → 6.56 | 52.7% | 29.88 → 21.63 | 33.51 → 29.34 |
| 125单位交战 | 26.17 → 11.34 | 56.7% | 65.44 → 34.37 | 77.73 → 42.39 |
| 驻军全景 | 14.12 → 5.81 | 58.9% | 32.28 → 19.20 | 36.70 → 22.13 |
| 暂停 | 7.01 → 0.99 | 85.9% | 15.14 → 13.54 | 17.01 → 19.57 |

村落和生产场景的整帧尾部在本机共享负载下反而变慢，不能把脚本节省等同为显示帧率提升。交战两次基线的脚本平均分别为22.33/30.01毫秒，优化版为11.84/10.84毫秒；四轮整机平均CPU为53.4%、52.3%、57.6%、47.9%。因此这些百分比是本次成本观测，不是跨机器稳定增幅。

| 村落 | 826 → 821 | 59.3 → 45.3 | 0 → 0 |
| 九设施生产 | 1067 → 1062 | 82.9 → 47.6 | 0 → 0 |
| 77单位驻军 | 3742 → 3737 | 24.9 → 26.5 | 15 → 5 |

整帧统计没有证明重战场稳定60FPS；6301次绘制调用仍是后续可测量的优化空间。本轮没有通过删除单位、裁掉画面或降低画质换取速度。更早的探索样本 `probe`、`baseline-a1`、`optimized-b1`、`fixed-*` 不用于上述结论；其中一组绘制数量不匹配，已排除。最终有效样本为 `paired-a1/b1/a2/b2`，含匹配的镜头、窗口、画质、玩法状态与绘制数量。

## 内存与回归范围

原生引擎静态内存中位数：村落163.3→163.5 MiB，125单位交战180.3→180.9 MiB；新增索引和姿势缓存有小幅常驻开销，本轮没有声称节省内存。原生游戏进程RSS峰值在四轮中为约478–577 MiB，包含资源载入和场景切换。

Web正式导出中Godot静态内存监控器返回0，视为不可用，不能据此报告0字节内存；采用CDP的JS堆及浏览器相关进程RSS进行观察。短期重开观察不能替代45–60分钟及真实手机的内存稳定性测试。

性能等价/探针42项、公共玩法109项、工种运输65项、动作接触60项、岛寨14项和模型净空5项通过。当前导出包完成H5真实键鼠/触控模拟、Dora原生16项操作以及工种/运输实际输入回归；牛车入库9石，486次脚底样本最大穿地约6.72e-7格，实际手部目标最大误差0.00537格。工作/行走各96帧重新捕获并检查关键帧。

## H5实际输入观测

四次分别启动独立浏览器，加载实际导出PCK，通过同一组建设/募兵操作进入场景；未注入资源或单位。H5按真实时间运行，具体角色位置、建设时刻和CPU负载没有锁成完全相同的模拟帧，所以这里只报告观测，不将其替代前述严格的原生内容对照。

| 场景 | 基线两轮脚本均值 | 优化B1脚本均值 | 优化B2脚本均值 | 基线P95范围 | 优化B1整帧P95 | 优化B2整帧P95 |
| --- | --- | --- | --- | --- | --- | --- |
| 村落 | 3.30 | 1.37 | 1.36 | 19.24–19.80 | 69.29 | 19.30 |
| 生产 | 4.77 | 4.06 | 2.75 | 20.66–21.20 | 109.44 | 21.90 |
| 募兵后 | 6.05 | 6.24 | 4.86 | 22.30–22.70 | 94.65 | 83.66 |
| 全景 | 6.37 | 7.39 | 3.55 | 22.80–23.10 | 121.52 | 23.40 |
| 暂停 | 4.19 | 1.02 | 1.02 | 18.53–19.00 | 120.48 | 18.60 |

B1出现持续长渲染间隔，B2的募兵段也有一段长帧；这些结果没有删除。B2募兵段整机CPU样本峰值70%，但现有观测不足以把所有长帧归因于共享负载，缺少逐帧GPU/调度追踪，原因仍未完全定位。其他B2场景及五次重开段约60次引擎渲染回调/秒，不等于显示器稳定60FPS。此轮交付明确通过功能与CPU成本回归，浏览器长帧仍是已知限制。

B2同一页面观察跨度约158秒，包含五次真实按钮重开。浏览器相关进程RSS总和采样峰值约1386 MiB；五次重开末尾分别为1320、1273、1280、1247、1269 MiB，未呈连续增长。此数包含共享页重复计数，且不是数十分钟或真机内存验收。重开观察器已处理场景重载期间只读状态暂时缺失；首次因此中断的采样保留在 `web-b2-before-restart-fix.json`，不作为完成的重开验收。

## 共用浏览器实例的补充诊断

独立浏览器运行出现长帧后，另在同一浏览器中按A/B/A/B导航至两版村落。每次预热5秒、观察约15秒，采集NVML整卡GPU利用率、整机CPU、CDP任务耗时及GPU进程ID；这组用于检查运行环境影响，不纳入前述四轮原生统计。

| 轮次 | 整帧P95 ms | 脚本平均 ms | 整机CPU平均 | GPU利用率范围 | 绘制中位数 |
| --- | --- | --- | --- | --- | --- |
| A1 | 141.02 | 17.69 | 100.0% | 12–99% | 860 |
| B1 | 72.28 | 3.84 | 100.0% | 10–99% | 820 |
| A2 | 79.62 | 10.87 | 99.9% | 7–67% | 820 |

四轮绘制中位数见表；A1与其余轮次也存在少量差异。主GPU进程持续存在，B1还短暂记录到第二个GPU进程，不能称所有渲染进程完全固定。原版也重现长帧，前三段整机CPU几乎满载，因此不能把先前独立进程的所有慢帧判定为代码回退。优化版的脚本成本仍较低；稳定帧率结论需要独占硬件窗口及逐帧GPU计时。原始数据在 `web-process-pair/report.json`，脚本为 `scripts/check-web-performance-pair.py`。
